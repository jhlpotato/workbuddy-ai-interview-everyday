【方向】

AI Agent — 任务规划与反思机制（Planning & Reflection：ReAct / Plan-and-Execute / ToT 范式选型、长任务防跑偏、动态重规划、Reflexion 经验沉淀，理论原理 + 系统设计 + 编码实现）

【题目及项目背景】

某头部券商研究所要打造"深度行业研究报告 Agent"（Research Agent）：分析师输入一句研究需求（如"对比储能与锂电回收两个赛道近三年的格局变化，给出配置建议"），Agent 自主完成检索行业数据、抓取政策原文、跑数据清洗与测算、生成图表、撰写万字报告并校验引用，端到端 30~60 步，单任务耗时 10~40 分钟。技术栈：FastAPI + 自研编排框架（不依赖 LangChain）、DeepSeek/Qwen 系列模型（规划用强模型、执行用轻量模型）、工具包括 Web 检索、数据库查询、Python 沙箱、文档生成。

第一版实现是纯 ReAct 单循环：模型走一步看一步，Thought → Action → Observation 直到认为报告写完。灰度两个月暴露四类典型问题：

  1. 目标漂移（跑偏）：执行到第 20 步后模型忘记初始研究目标，围绕某个子问题反复检索打转，最终报告缺失关键章节（如漏掉竞争格局），个别任务陷入无效循环烧光 Token 预算；
  2. 前置假设被推翻只能重跑：任务推进到一半才发现两家公司的营收口径不一致（一个为并表、一个为单表），此前所有测算作废——但系统只会从头执行整个任务，单次浪费数十万 Token；
  3. 无校验的一次性输出：报告结论与数据对不上（模型在没有证据的情况下编造结论），没有质检环节，分析师返工率高；
  4. 全程串行、延迟爆炸：明明多个子课题（政策梳理、数据拉取、竞品调研）互相独立可并行，全部串行执行，用户端 P95 等待超 40 分钟。

面试题：请给出该 Research Agent 的规划与反思体系完整设计方案，重点阐述：① ReAct / Plan-and-Execute / Reflection / ToT 四种范式的原理、优缺点与选型，以及本案例应该采用什么混合策略；② 任务拆解的方法论（目标层/子任务层/能力映射层、粒度判据、DAG 依赖与并行）；③ 动态重规划的触发条件、计划状态管理与"局部重排而非全量重跑"如何落地；④ 反思机制设计：触发时机、证据驱动反馈、Reflexion 与一次性自检的区别、如何防"为改而改"并沉淀可复用经验；⑤ 手写 Planner-Executor-Reflector 核心执行循环代码。

【答案详解】

一、原理讲解：四种范式对比与混合策略——先选对流程，再谈调优

Agent 规划的本质是把"想清楚"和"做出来"在时间轴上如何分配。四种主流范式回答的是不同问题：

范式核心机制优点缺点适用场景
ReActThought → Action → Observation 循环，边想边做灵活、实现简单、工具结果能改变下一步无全局视野，长任务易跑偏/忘目标/无效循环路径不确定的短链路探索任务
Plan-and-ExecutePlanner 先输出完整计划，Executor 按计划逐步执行全局可控、长任务不跑偏、可并行、省 Token初始计划出错不可逆，遇计划外突发易卡壳步骤较稳定、依赖明确的长周期任务
ReflectionGenerate → Critique → Refine 闭环，初稿后增加检验修订环节大幅降幻觉、提质量（HumanEval 上 GPT-4 直接生成 80%，叠加 Reflexion 升至 91%）每轮反思新增 1~3 次模型调用，Token 与延迟翻倍低容错高严谨场景：代码、报告、金融分析
ToT（思维树）分叉点同时展开多条候选路径，评估器打分、可回溯能探索多解、适合博弈/推导成本与复杂度最高数学推导、复杂代码生成、逻辑博弈

三条必答的原理认知：

  1. Reflection 的本质是上下文压缩：LLM 没有真正的记忆，每次调用都从零开始。反思机制把上一轮学到的教训压缩成高密度"经验"文本，塞进下一轮上下文——相当于给 Agent 一个错题本。Reflexion 与"简单自检"的区别在于：一般的 Reflection 只是一次输出自检，Reflexion 强调经验在多次尝试之间被保留和复用（用文字化经验替代梯度更新），并且反思内容必须是结构化的"错误证据 + 可能原因 + 下次动作 + 适用范围"，而不是泛泛要求"更认真"。
  2. 规划与执行解耦是可靠性工程的第一原则（InfoQ Agentic AI 架构系列反复强调）：非确定性的模型负责提出计划，确定性的软件框架负责执行、校验与状态管理——把不可预测的部分隔离在"提出建议"的环节。模型输出必须当作不可信输入，计划 JSON 要做 Schema 校验、节点白名单过滤后才能驱动执行器。
  3. 选型的核心原则是"不为不需要的能力买单"：Anthropic《Building Effective Agents》主张从最简单可行的 workflow 起步；简单问答用 ReAct 就够，叠加 Reflection 反而增加延迟与成本，只有明确遇到"质量不够"问题才升级范式。

本案例的混合策略（工业标准答案）：外层 Plan-and-Execute（强模型 Planner 一次性拆解研究大纲，防长任务跑偏、支持子课题并行）→ 内层单步用 ReAct（每个子课题内部边检索边调整，保持灵活性）→ 关键节点叠加 Reflection（报告成稿后数据核对、引用校验、章节完整性验收）。一句话：Plan 控全局、ReAct 做执行、Reflection 保质量。

二、任务拆解方法论：三层拆解 + 粒度三条判据

面试高频陷阱是回答"拆成几个步骤写 prompt"——这不算拆解。真正的任务拆解分三层：

层次内容示例（研究报告任务）
目标层（Goal）不是"做什么"，而是"做到什么程度算完成"——可验收的完成判据❌"分析储能赛道" ✅"输出含市场规模测算、竞争格局、政策梳理、配置建议四章，每个结论有数据引用"
子任务层（Subtasks）拆成可执行单元，明确依赖关系形成 DAG政策检索 → 数据拉取 → 口径核对 → 测算 → 撰写 → 审校；其中政策/数据/竞品三支可并行
能力映射层（Tools/Skills）每个子任务映射到具体能力（工具/API/模型）数据获取→SQL 工具；测算→Python 沙箱；撰写→强模型；审校→Reflection 环节

粒度判据（比"适中就好"值钱的具体标准，三条全满足才算拆对了）：

  1. 这一步能否独立验证结果（做完能检查"行数列数对不对"，而不是说不清何时算完成的"处理数据"）；
  2. 这一步失败后能否独立重试（不用连带前面的步骤一起重跑）；
  3. 这一步的产出能否被后续步骤直接消费。

规划粒度的锚点是"可验证的中间产物"：每一步都有一个明确的、可检查的产出。太粗的规划等于没做（每步内部还是黑盒），太细的计划比任务还长且一步失败全盘皆废。

防幻觉规划：让模型输出受约束的计划 JSON（子任务列表 + 依赖边 + 每步验收判据 + 工具白名单），执行器只接受 Schema 合法且节点在白名单内的计划；关键流程（合规校验、发款类动作）固化在代码里，不交给模型自由发挥。评价规划质量的指标：任务完成率、无效步骤数、重规划次数与耗时——不是计划文字写得是否详尽。

三、动态重规划：触发条件、计划状态管理与局部重排

第一版方案"前置假设被推翻只能从头重跑"的病根，是把计划当成了死文档。正确的心理模型不是"规划然后执行"，而是"规划一个足够好的起点，然后在执行中持续修正"——Agent 每一步都会拿到规划时不存在的新信息。

重规划的四类触发条件：

  1. 步骤执行失败（工具报错、连续重试不通过）；
  2. 关键事实推翻前置假设（本案例的口径不一致：发现"两家公司营收口径不同"，意味着所有依赖该假设的已产出结论失效）；
  3. 目标/需求变化（用户中途追加要求）；
  4. 环境变化（检索到新政策使既有结论过时）。

计划状态管理（重规划能落地的前提）：任务状态需记录每个步骤的版本、输入依据、产物、重试次数与结束原因。规划器维护的是一份"活计划"：

  • 已完成步骤记录其产物与所依赖的假设清单；
  • 假设被推翻时，沿依赖边（DAG）定位所有受影响的下游步骤，只重排受影响的剩余分支，已验证的前序产物直接复用——这就是"局部重排而非全量重跑"，直接把本案例的数十万 Token 浪费降下来；
  • 重规划次数设上限（如 3 次），重复失败转澄清、降级或人工，防止"重规划循环"本身成为新的死循环；
  • 世界变化后不能沿旧计划提交：如确认环节之后库存已变，必须重新查询并请求确认新方案。

四、反思机制设计：证据驱动、防"为改而改"、经验沉淀

触发时机（宁可少而准）：测试/校验失败之后、工具异常之后、关键阶段完成之后、最终答案验收失败之后。反思是正式运行时范式而非调试辅助，每次反思都有真实的 Token 与延迟代价。

证据驱动的反馈源优先级：优先用测试、业务回执、可核查证据作为反思输入（如"Python 沙箱断言失败：结论段落引用的增速 23% 与数据表计算的 15% 不符"），而不是让模型自己评自己——自评模型可能强化错误解释。反思输出必须是结构化四元组：错误证据 + 可能原因 + 下次动作 + 适用范围。

防"为改而改"（面试必答的追问点）：

  1. PASS 退出机制：审阅环节输出 PASS / FAIL 二值判定，PASS 即终止反思循环——没有新证据时反复改写同一答案不能带来可靠提升；
  2. 硬性 max 轮次（反思轮次上限，通常 2~3 轮）；
  3. 对照基线验证价值：限制次数、对照无反思基线，确认反思真的在提升而不是在波动。

经验沉淀（Reflexion 精髓）：反思产出不是用完即弃，而是写入经验库（按任务类型索引），下次同类任务的 Planner 注入"历史失败模式"（如"该公司口径数据先核对是否并表"）。经验要允许过期或撤回（衔接记忆治理：过期/降权/删除语义不同）。注意：反思本身也增加成本，简单任务不值得；衡量反思体系用完整任务成功率、错误副作用与成本，不能只看反思文字是否漂亮。

五、编码实现：Planner-Executor-Reflector 核心执行循环

import asyncio, json
from dataclasses import dataclass, field

@dataclass
class Task:
    id: str
    goal: str                      # 子任务目标（含完成判据）
    deps: list = field(default_factory=list)   # 依赖的前置任务 id（DAG 边）
    tool: str = "llm"              # 能力映射：检索/SQL/沙箱/文档/llm
    status: str = "pending"        # pending/running/done/failed/blocked
    result: str = ""
    retries: int = 0
    assumptions: list = field(default_factory=list)  # 本步依赖的前置假设

class PlanExecuteReflectAgent:
    """外层 Plan-and-Execute + 内层单步灵活 + 关键节点 Reflection。
    核心：受约束计划 JSON、DAG 拓扑并行、假设失效局部重排、
    证据驱动反思、PASS 退出 + 轮次上限 + 重规划预算。"""

    def __init__(self, llm_planner, llm_executor, tools, max_replan=3, max_reflect=3):
        self.planner, self.executor, self.tools = llm_planner, llm_executor, tools
        self.max_replan, self.max_reflect = max_replan, max_reflect
        self.lessons: list[str] = []   # Reflexion 经验库（跨尝试保留，按任务类型索引）

    async def run(self, user_goal: str) -> str:
        for replan in range(self.max_replan + 1):
            plan = await self._make_plan(user_goal)          # ① 受约束规划
            for round_ in range(self.max_reflect + 1):       # ② 反思轮次上限
                ok, evidence = await self._execute_dag(plan) # ③ 拓扑并行执行
                if ok:
                    return await self._final_review(plan, evidence)  # ④ 验收
                verdict = await self._reflect(plan, evidence)  # ⑤ 证据驱动反思
                if verdict["decision"] == "PASS":              # PASS 退出，防为改而改
                    return evidence
                if verdict["decision"] == "REVISE_PLAN":
                    self.lessons.append(verdict["lesson"])     # 经验沉淀
                    user_goal += f"\n[历史教训] {verdict['lesson']}"
                    break                                      # 跳出反思轮 → 重规划
                # decision == PATCH：仅修补当前输出，带着反馈重跑本轮
        return "已达重规划上限，输出当前进展与未解决问题清单，转人工处理。"

    async def _make_plan(self, goal: str):
        lessons = "\n".join(f"- {x}" for x in self.lessons[-5:])  # 注入历史失败模式
        raw = await self.planner(
            f"将目标拆解为子任务 JSON 列表：[{{id,goal,deps,tool,assumptions}}]。\n"
            f"要求：每步有可验证的完成判据；独立子任务不设依赖以便并行；"
            f"tool 只能取 {list(self.tools)}。\n历史教训：\n{lessons}\n目标：{goal}")
        tasks = [Task(**t) for t in json.loads(raw)
                 if t["tool"] in self.tools]        # 白名单过滤，拒收越权节点
        return tasks

    async def _execute_dag(self, plan: list[Task]):
        evidence, by_id = {}, {t.id: t for t in plan}
        done = set()
        while len(done) < len(plan):
            ready = [t for t in plan if t.id not in done
                     and all(d in done for d in t.deps)]
            if not ready:
                return False, "存在不可满足的依赖环或失败前置，无法继续"
            results = await asyncio.gather(*[self._run_step(t, evidence) for t in ready])
            for t, (ok, out) in zip(ready, results):
                if not ok:
                    return False, f"步骤 {t.id}({t.goal}) 失败: {out}"
                by_id[t.id].status, evidence[t.id] = "done", out
                done.add(t.id)
        return True, json.dumps(evidence, ensure_ascii=False)

    async def _run_step(self, t: Task, evidence: dict):
        ctx = "\n".join(evidence[d] for d in t.deps)       # 只喂依赖步骤的产物
        try:
            out = await self.executor(f"任务: {t.goal}\n判据: 见目标\n上下文:\n{ctx}")
            return True, out[:2000]                        # 产物截断，防上下文膨胀
        except Exception as e:
            return False, f"{type(e).__name__}: {e}"       # 错误即证据，不吞异常

    async def _reflect(self, plan: list[Task], evidence: str):
        resp = await self.planner(
            "对照以下证据做审阅，输出 JSON {decision, lesson}。\n"
            "decision 取值: PASS(证据充分) / PATCH(小瑕疵附修正意见) / "
            "REVISE_PLAN(前置假设被推翻或结构缺失，需调整计划)。\n"
            "lesson 必须是『错误证据+原因+下次动作+适用范围』四元组。\n"
            f"证据：{evidence[:6000]}")
        return json.loads(resp)

    async def _final_review(self, plan: list[Task], evidence: str) -> str:
        # 终审：结论必须逐条可追溯到证据 id，否则拒收（回应背景问题 3 的幻觉结论）
        return await self.planner(f"基于证据撰写最终报告，每个结论标注证据编号，"
                                  f"无证据支撑的观点必须删除。\n证据：{evidence[:8000]}")

代码讲解（面试官追问点）：① _make_plan 强制受约束 JSON + 工具白名单过滤，并把历史教训注入 Planner——体现"模型提议、代码把关"与 Reflexion 经验复用；② _execute_dag 按依赖拓扑分波次执行，波内 asyncio.gather 并行——独立子课题（政策/数据/竞品）并发跑，直接回应背景问题 4 的串行延迟；③ 步骤失败立即返回结构化证据（步骤 id + 失败原因），由上层决定重试/重规划，执行器本身不做静默重试；④ _reflect 三值决策（PASS/PATCH/REVISE_PLAN）+ max_reflect 轮次上限防"为改而改"，REVISE_PLAN 才触发重规划、PATCH 只修补当前输出——避免小瑕疵也推倒重来；⑤ 重规划由 max_replan 兜底，超限输出进展清单转人工——防止"重规划循环"成为新死循环；⑥ 局部重排的要点在 Task 的 assumptions 与 deps：假设被推翻时沿依赖边定位受影响分支重排、已验证产物（evidence）复用，本示例为可读性做了简化，生产中需把"假设失效 → 下游失效"做成 DAG 反向传播；⑦ 每步产物截断 + 只喂依赖步骤的产物，控制长任务的上下文体积；⑧ 可观测：每轮记录计划版本、步骤耗时、Token、反思决策，支持整任务回放定位"哪一步开始跑偏"。

答题点睛：一段话收束——"长任务 Agent 的规划体系是三层混合：外层 Plan-and-Execute 用强模型拆出带验收判据的 DAG 计划防跑偏、内层 ReAct 保持单步灵活、关键节点 Reflection 用证据驱动反思保质量；拆解粒度对齐'可独立验证、可独立重试、产出可直接消费'的中间产物；执行中把计划当活文档——步骤版本、输入依据、产物、假设清单全部落状态，假设被推翻就沿 DAG 局部重排复用产物，而不是全量重跑；反思靠 PASS 退出、轮次上限和结构化教训防'为改而改'，教训沉淀成经验库反哺下次规划；最后用完成率、无效步数、重规划次数和 Token 成本衡量这套体系，而不是看计划写得多漂亮。"
