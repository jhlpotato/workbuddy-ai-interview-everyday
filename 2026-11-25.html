【方向】

AI Agent — 编码智能体（Code Agent）系统设计（Agent Loop 核心循环与终止治理、仓库上下文引擎与渐进披露、编辑表示与 diff 应用、执行反馈闭环与沙箱、上下文压缩与长任务 Harness、安全护栏与回滚，理论原理 + 系统设计 + 编码实现）

【题目及项目背景】

某开发者工具公司（服务约 2000 家企业客户、日活开发者约 15 万）要打造一款企业级编码智能体（Code Agent）：开发者用自然语言描述任务（如"把订单服务的支付回调改成幂等，并补齐回归测试"），Agent 在仓库内自主完成理解代码 → 规划改动 → 多文件编辑 → 运行构建与测试 → 根据报错自我修复 → 输出可评审的 diff/PR。产品形态对标 Claude Code（终端 Agent）、Cursor Composer（IDE 内 Agent）与 Devin（长时自主 Agent），单任务典型执行 15~40 步、耗时 3~15 分钟，涉及读代码、编辑、执行 shell 命令三类工具。

团队第一版实现是"全量上下文 + 全文件重写 + 直接在本机执行"：把模型认为相关的文件整个塞进上下文，让模型输出完整的新文件内容直接覆盖，命令在开发者本机 shell 执行。灰度一个月暴露四类典型问题：

  • 大仓库上下文放不下、且塞进去也没用：单体仓库超过 50 万行代码，相关文件全量注入动辄数十万 token，成本爆炸且超出窗口；而一旦改用向量检索，索引又频繁过时（代码天天在改），召回一堆改名前的旧函数，模型基于陈旧上下文写出的代码编译都过不了；
  • 全文件重写又贵又危险：让模型重写一个 800 行的文件，只为改 3 行——token 成本是 diff 的几十倍，且重写时容易"顺手"改动无关逻辑、丢掉末尾函数（大文件截断），一次误覆盖让同事的半成品功能直接丢失，且没有任何回滚手段；
  • 死循环与预算失控：测试失败后模型用完全相同的 patch 反复重试，单任务跑到 60+ 轮还没停；个别任务上下文被巨大的测试日志撑爆后模型开始胡言乱语，把无关文件改得一塌糊涂；
  • 安全与信任危机：Agent 在本机 shell 里执行了 git push --force 和一条删库的清理脚本；企业客户质疑"我的代码会不会被拿去训练、Agent 会不会偷偷联网把代码发出去"，销售侧被逼着逐条解释。

面试题：请给出该编码智能体的完整设计方案，重点阐述：① 为什么生产级 Code Agent 的骨架是"简单循环（loop）而非复杂状态图（graph）"，核心循环的标准形态与四类终止条件（done 工具 / 步数上限 / 预算上限 / 停滞检测）如何设计；② 仓库上下文引擎怎么建：混合策略（常驻规则文件 + 渐进披露 + Agent 自主探索）为什么优于纯向量索引，Cursor 式增量索引（Merkle 树 + Tree-sitter AST 切分 + 混合检索）的管线与适用边界；③ 编辑表示如何选型（全文件重写 vs unified diff vs search/replace block），diff 打不上（模糊锚点）如何兜底，为什么要原子应用与 checkpoint 回滚；④ 执行反馈闭环：为什么"测试/linter/编译器是免费的完美 critic"、不需要 LLM critic；上下文污染治理（工具结果截断、历史压缩 compaction、子代理干净上下文、结构化笔记与 context reset）如何落地；⑤ 安全护栏：沙箱隔离、权限分级、写门槛与不可逆操作拦截、防死循环预算控制，以及如何用 SWE-bench 类基准做发布门禁；⑥（编码）现场实现核心 Agent Loop + 编辑应用器 + 安全护栏的最小可用代码。

【答案详解】

一、核心循环：为什么是"简单 loop"而不是"复杂 graph"

1. 生产系统的收敛结论。 Claude Code、Codex、Cursor 的底层是同一个东西——一个 while 循环：模型产出工具调用就执行、把结果喂回去、直到模型不再调用工具或触发预算。早期的复杂 DAG 方案（"用户想 X 就去节点 A"）被普遍放弃，因为每条硬编码的转移都是一个潜在故障点，而现代模型完全有能力在循环内自己探索、犯错、自我修正。工程共识可以概括为一句话：循环本身已经没有秘密，秘密全在循环外面——上下文管理、安全控制、优雅降级、成本约束才是决定 Agent 能否进生产的关键。

2. 标准循环形态。


while True:
    resp = model.generate(system + memory + history + tools)
    if resp.tool_calls 为空: break          # 模型给出最终答案
    results = execute_tools(resp.tool_calls) # 并行执行 + 安全护栏
    history.append(results)                  # 观察回灌，驱动下一轮

它的进化分三个段位：Level 1（LLM + Tools 直调）只够做 demo；Level 2 把记忆读写放进循环（调用前读、工具执行后写），循环从"工具调用量传输带"变成推理引擎；Level 3 在循环外再包一层 Harness——记忆层（CLAUDE.md 类规则文件每轮注入）、反馈层（测试/Linter 报错自动回灌形成自修复闭环）、编排层（大任务拆成有验收标准的子任务，防止无终点空转）。

3. 四类终止条件缺一不可（这是面试必考点，缺任何一个都会在长任务上翻车）：

终止条件作用典型实现
显式 done 工具模型主动宣告完成，优于"输出纯文本即结束"的模糊信号强制要求调用 task_done(summary) 才算结束
max_iters 步数上限兜底防失控，编码 Agent 经验值 20~30 轮（Claude Code 单个子任务默认 25）硬编码在 Harness，不接受提示词覆盖
预算上限（token/美元）把成本从"事故"变成"参数"网关侧累计计费，超限暂停并通知用户
停滞检测治"重复调用相同工具+相同参数"的死循环维护 (tool, 参数哈希) 近期集合，重复 N 次即升级人工

注意：提示词里写"不要死循环"防不住——与 Prompt Injection 同源，模型输出是不可信的。终止逻辑必须由 Harness 代码保证，这正是 AutoGPT"无限烧钱"教训之后的行业共识：每个后续 Agent 设计都在补这四条。

4. 主流产品的形态对照（体现"同一循环、不同外壳"）：Claude Code 是 ReAct 循环 + TodoWrite 外置计划 + 子代理派发；Cursor Agent 是同型循环 + 编辑器内 diff 预览/接受作为每步人工闸门；Devin 是显式 Planner-Executor-Verifier 三段 + 云端持久 VM；Aider 循环极短（读文件 → 提 diff → 应用 → 跑测试），因为任务类别有界，紧凑恰恰是优点。

二、仓库上下文引擎：混合策略优于纯向量索引

1. 为什么"全量塞入"和"纯 RAG"都不对。 全量塞入受限于窗口与成本；纯向量索引有致命缺陷——代码是强结构、强关键词的文本，且天天在改，索引天然滞后。Anthropic 在上下文工程文章中给出的结论是混合策略：少量高价值常驻上下文（CLAUDE.md 项目规则）直接预置进上下文，其余交给 Agent 用 glob/grep/读文件等原语自主探索、渐进披露（progressive disclosure）——每次交互产出的信息（文件名、目录结构、import 关系）决定下一步看哪里，Agent 像人一样逐层建立理解，只把必要内容留在工作记忆里。这样做的好处是永远不会引用过时索引（看到的永远是磁盘上的真实文件），代价是探索多花几轮。Claude Code 正是该模式的范本：CLAUDE.md 预置 + grep/glob 即时检索，绕开了陈旧索引与复杂语法树的维护成本。

2. 需要预计算索引时的标准管线（Cursor 式）。 当仓库巨大、探索成本过高时，Cursor 的做法值得抄：

  • Merkle 哈希树增量索引：按文件树算哈希，只重嵌自上次索引以来变化的文件，避免全量重扫；
  • Tree-sitter AST 结构化切分：按函数/类/接口边界切块，而非固定 token 窗口——代码检索的正确单位是"符号"而不是"段落"；
  • 混合检索：向量（HNSW）+ BM25 关键词倒排双路召回，Cross-Encoder 重排取 Top-N；代码问题里"精确符号名"的场景极多，纯语义召回会答非所问；
  • 父子上文：检索命中函数级 chunk，注入时带上所属文件骨架，兼顾精度与完整语境。

3. 分层上下文设计（与 Prompt Caching 联动）。 上下文应分三层：常驻层（系统提示 + 工具 Schema + 项目规则）保持精简稳定，是前缀缓存命中率的基础；领域层（Skills/操作手册）按需加载，触发由工程侧每轮扫描保证，不能指望模型自己记得；运行时层（文件内容、命令输出）动态注入、用完即可截断。这也解释了为什么同一个模型在 Cursor/Claude Code/Windsurf 上效果天差地别——选工具选的是上下文工程的实现水平。

4. Aider 的 repo map 是第三条路线：不走向量库，而是用 tree-sitter 抽取全仓库符号表生成一张"仓库地图"（每个文件的符号签名列表）常驻上下文，模型看地图决定打开哪些文件。实现轻、无索引过时问题，适合中小仓库，是面试中体现方案多样性的加分项。

三、编辑表示与 diff 应用：从"全文件重写"到"结构化补丁"

1. 三种格式对比：

编辑格式优点缺点结论
全文件重写无需对齐、最不易失败token 成本随文件大小线性膨胀；长文件易截断丢内容；模型"顺手"改无关代码仅适合小文件/新建文件
unified diff精确省 token；人类可读可评审模型算不准行号，@@ 偏移经常错不建议让模型直接产出
search/replace block（Aider/Claude Code Edit 风格）模型只需复制原文再给新文，无需行号；成功率最高原文匹配失败需兜底生产主流

2. 模糊锚点兜底。 模型复制的"原文"经常与磁盘内容有细微出入（空白差异、轻微改写）。落地要点：精确匹配失败 → 做空白归一化匹配 → 再失败用模糊匹配（编辑距离/锚点对齐，类似 Myers diff 的模糊 anchor）在文件中定位最相似区段，相似度低于阈值才报错把冲突信息回灌给模型重试。Aider 的实践表明，这一层"容错应用器"是 search/replace 方案能用起来的关键——Agent 的编辑成功率瓶颈往往不在模型，而在 patch 应用器。

3. 原子应用与 checkpoint 回滚（不可妥协的工程底线）。 每次文件变更前先落 checkpoint（git commit 或快照），patch 原子应用：要么全部成功要么全部回滚，绝不留下半编辑状态；整个任务提供一键回滚到任务起点。这既是安全网（模型改坏可恢复），也是信任前提（用户敢放手让 Agent 跑）。

4. 为什么"diff 而非重写"同时也是上下文治理：diff 输出只包含变更行，token 少一个数量级、错误概率更低，还天然适配 IDE 的 diff 预览/逐块接受交互（Cursor 把它做成每步人工闸门）。

四、执行反馈闭环：免费的完美 critic 与上下文治理

1. 代码是"反馈最廉价"的 Agent 领域。 学术界试过 Actor-Critic 双模型（一个改、一个审），但工程上基本被淘汰，原因一句话：跑测试是免费、确定、完美的 critic——编译器告诉你能不能解析，测试套件告诉你对不对，Linter 告诉你干不干净，没有任何 LLM critic 比得上"测试通过"这个信号。所以编码 Agent 的核心闭环是：改代码 → 跑构建/测试 → 解析失败信息 → 结构化回灌 → 模型自修复。面试加分点：如果在编码 Agent 里想加 LLM critic，先自问"测试/Linter/类型检查能不能给同样信号"——免费 critic 永远优于学习出来的 critic（LLM critic 的正确用武之地是反馈缓慢、噪声大、缺失的领域，如研究型 Agent）。

2. 上下文污染治理四件套（案例里"测试日志撑爆上下文后胡言乱语"的解法）：

  • 工具结果截断：在 formatter 层把命令输出按行数/字节截断，错误信息保留头尾、中间折叠；这是治"上下文炸弹"的第一杠杆；
  • Compaction 压缩：历史接近窗口上限时，让模型把对话史压缩成摘要再重开窗口——保留架构决策、未解决 bug、实现细节，丢弃陈旧的原始工具输出（工具结果一旦用完就没必要留着原文）；调优原则是先最大化召回再提精度；
  • 子代理干净上下文：探索性、产出巨大的子任务（读一堆文档找答案、跑长测试）派给子代理，它返回结论而非过程，避免污染主循环（Claude Code 的 Task 工具即此模式；但注意 Anthropic 新 guidance：新模型能力足够时优先收敛到单循环，子代理按"上下文边界"划分而非按问题类型划分，避免电话游戏式的信息衰减）；
  • 结构化笔记 + Context Reset：长任务跨多个上下文窗口时，让 Agent 把计划与进度写进持久产物（TodoWrite、progress 文件、feature 清单），新窗口的 Agent 靠"笔记 + git 历史"快速恢复状态——Anthropic 长时 Agent 实验的关键发现是：光靠 compaction 不够，模型会有"上下文焦虑"（临近窗口上限就草草收工）与一次性 one-shot 大任务的倾向，_initializer agent 建环境 + coding agent 每窗口增量推进并留干净状态_ 的双角色 Harness 才能跨窗口持续工作；planner/generator/evaluator 三代理结构还能治"自我评价偏宽松"的问题。

3. 落地清单：每轮记录完整 Thought/Action/Observation trace（不记 trace 就无法归因失败）；命令一律设超时并自动杀后台进程；把"半成品修改"写成可验收的子任务粒度，一个窗口只推进一个 feature。

五、安全护栏：模型永远不是安全边界

1. 沙箱隔离。 Agent 执行的每条 shell 命令都不可信。云端方案按会话起隔离环境（容器/Firecracker microVM，配网络白名单与资源上限）；本机方案（Claude Code 类）必须至少做到：文件系统读写范围限定在项目目录、网络默认禁用或白名单、命令在低权限用户/命名空间中执行。能力再强的模型也不能给它"直接跑在本机用户态"的信任。

2. 权限分级 + 写门槛 + 不可逆拦截。 工具按风险分级：读操作自动放行；写操作按范围决定是否需要确认（Cursor 的 diff 逐块接受即是写门槛的交互形态）；不可逆操作（git push --force、删库、外发数据）由硬编码护栏层拦截——护栏是确定性代码而非提示词，命中即强制人工批准或直接拒绝。所有确认必须可撤销、默认最小权限。

3. 防死循环与预算：见第一节四类终止条件，强调预算上限和重复检测必须在 Harness 侧实现。

4. 隐私与合规（企业客户三连问的标准答案）：企业版提供零数据保留（ZDR）协议与 Privacy Mode（本地 embedding、不落服务端）；代码索引支持客户端侧本地化；以 SOC 2 等认证作为合同要求。

5. 发布门禁：用 SWE-bench Verified 类真实缺陷修复基准构建评测 Harness，模型/prompt 每次变更先跑基准回归，达标才发布——"改 prompt = 改代码"拥有同等回归纪律。

六、核心代码：Agent Loop + 编辑应用器 + 安全护栏


# code_agent.py — 编码智能体最小可用内核
# 三层结构：AgentLoop（循环+终止治理）/ PatchApplier（编辑应用）/ Guard（安全护栏）
import re, json, hashlib, subprocess, difflib
from dataclasses import dataclass, field
from pathlib import Path

MAX_ITERS = 25
MAX_BUDGET_USD = 2.0
BANNED_PATTERNS = [r"rm\s+-rf\s+/", r"git\s+push\s+.*--force", r"drop\s+table", r"curl.*\|\s*sh"]

@dataclass
class Turn: role: str; content: str; tool_calls: list = field(default_factory=list)

class Guard:
    """确定性安全护栏：模型输出不可信，拦截必须由代码而非提示词保证"""
    @staticmethod
    def check_command(cmd: str) -> str | None:
        for p in BANNED_PATTERNS:
            if re.search(p, cmd, re.I):
                return f"被护栏拦截：命中不可逆/高危模式 {p}"
        return None

class PatchApplier:
    """search/replace 编辑应用器：精确匹配 -> 空白归一化 -> 模糊锚点兜底"""
    @staticmethod
    def _norm(s: str) -> str: return re.sub(r"[ \t]+", " ", s.strip())

    @classmethod
    def apply(cls, path: str, old: str, new: str) -> str:
        text = Path(path).read_text(encoding="utf-8")
        if old in text:                                    # 1) 精确匹配
            return Path(path).write_text(text.replace(old, new, 1), encoding="utf-8") or "ok"
        lines = text.splitlines(keepends=True); old_l = old.splitlines(keepends=True)
        # 2) 空白归一化匹配
        norm = [cls._norm(l) for l in lines]; nold = [cls._norm(l) for l in old_l]
        for i in range(len(norm) - len(nold) + 1):
            if norm[i:i+len(nold)] == nold:               # 命中：仅替换该区段
                lines[i:i+len(nold)] = [l + "\n" for l in new.splitlines()]
                Path(path).write_text("".join(lines), encoding="utf-8"); return "ok(fuzzy-ws)"
        # 3) 模糊锚点：找相似度最高的区段，低于阈值回灌错误让模型重试
        best, score = -1, 0.0
        for i in range(len(lines) - len(nold) + 1):
            r = difflib.SequenceMatcher(None, norm[i:i+len(nold)], nold).ratio()
            if r > score: best, score = i, r
        if best >= 0 and score > 0.9:
            lines[best:best+len(nold)] = [l + "\n" for l in new.splitlines()]
            Path(path).write_text("".join(lines), encoding="utf-8")
            return f"ok(fuzzy score={score:.2f})"
        return f"error: 匹配失败(最高相似度 {score:.2f})，请重新读取文件后给出精确原文"

@dataclass
class Budget:
    iters: int = 0; usd: float = 0.0
    recent: dict = field(default_factory=dict)   # (tool, 参数哈希) -> 连续出现次数

    def observe(self, tool: str, args: dict):
        key = (tool, hashlib.md5(json.dumps(args, sort_keys=True).encode()).hexdigest())
        self.recent[key] = self.recent.get(key, 0) + 1
        return self.recent[key] >= 3            # 同参数重复 >=3 次 → 停滞

class AgentLoop:
    def __init__(self, model, tools): self.model, self.tools = model, tools

    def run(self, task: str, cwd: str):
        history = [Turn("user", task)]; budget = Budget()
        for _ in range(MAX_ITERS):                       # 终止条件②：步数上限
            resp = self.model.generate(history)          # 终止条件④：预算累计在网关侧
            budget.usd += resp.cost_usd
            if budget.usd > MAX_BUDGET_USD: return "budget_exceeded: 已暂停并通知用户"
            history.append(Turn("assistant", resp.text, resp.tool_calls))
            if not resp.tool_calls:                      # 终止条件①：模型自然收尾
                return resp.text
            for call in resp.tool_calls:
                if err := self._dispatch(call, history, budget, cwd): return err
        return "max_iters: 达到步数上限，输出当前进度供人工接管"

    def _dispatch(self, call, history, budget, cwd) -> str | None:
        # 终止条件③：停滞检测 —— 相同工具+相同参数连续出现即升级人工
        if budget.observe(call.name, call.args):
            history.append(Turn("tool", "检测到重复停滞，已暂停，请人工确认下一步")); return "stagnation_paused"
        try:
            result = self.tools[call.name](**call.args, cwd=cwd)   # 工具内部再过 Guard
            summary = result if len(str(result)) < 2000 else str(result)[:2000] + "\n...[截断]"
        except Exception as e:
            summary = f"error: {type(e).__name__}: {e}"   # 失败结构化回灌，模型自修复
        history.append(Turn("tool", f"[{call.name}] {summary}"))
        return None

# 工具示例：run_cmd（护栏内）、edit_file（PatchApplier）
def run_cmd(cmd: str, cwd: str, timeout: int = 60):
    if err := Guard.check_command(cmd): return f"error: {err}"
    r = subprocess.run(cmd, shell=True, cwd=cwd, timeout=timeout,
                       capture_output=True, text=True)
    out = (r.stdout or "") + (r.stderr or "")
    lines = out.splitlines()
    return "\n".join(lines[:100] + ["...[截断]"] + lines[-20:]) if len(lines) > 120 else out

def edit_file(path: str, old: str, new: str, cwd: str):
    return PatchApplier.apply(str(Path(cwd) / path), old, new)

落地要点标注：Guard 是硬编码护栏（提示词防不住高危命令）；PatchApplier 三级匹配是 diff 成功率的关键；Budget.observe 即停滞检测；工具结果统一截断治上下文炸弹；每次 edit_file 前生产版应先 git stash/commit 落 checkpoint 支持一键回滚。生产化还需补齐：并行工具执行、结构化笔记（todo/progress 文件）与跨窗口 Handoff、SWE-bench 类回归门禁。
