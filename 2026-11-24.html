【方向】

AI Agent — Agent 评测体系（Agent Evals：结果/轨迹/系统三层指标、轨迹评估与匹配模式、LLM-as-Judge 偏差治理与校准、评测集构建与 CI 回归门禁、badcase 回流数据飞轮，理论原理 + 系统设计 + 编码实现，穿插 FDE 落地视角）

【题目及项目背景】

某在线旅游平台（OTA，月活约 4000 万）要为 App 与小程序上线"智能旅行顾问 Agent"：用户用自然语言描述需求（如"帮我规划一个 5 天的云南亲子游，预算 1 万，尽量直飞"），Agent 完成多轮需求澄清 → 查询机票/酒店/景点门票并比价 → 生成行程方案（天数、路线、预算分解）→ 确认后下单预订（写操作）→ 售后改签/退订。技术栈：FastAPI + 自研编排框架（不依赖 LangChain）、Qwen-Max 做规划与比价、Qwen-Plus 做执行与摘要、Milvus 支撑政策与产品知识 RAG、约 40 个工具（search_flight、search_hotel、get_refund_policy、create_order、cancel_order、modify_booking 等）。

Agent 上线三个月，日均 4 万次请求，其中约 8% 会走到真实下单。随后发生三件事，暴露了公司在"评测"上的系统性缺位：

  1. 一次"省钱式"改动引发回归事故：团队为降成本把比价环节的模型从 Qwen-Max 换成 Qwen-Plus，并顺手精简了 System Prompt。两周后客诉上升 3 倍——比价 Agent 开始跳过低价格位筛选，给用户推荐了明显偏贵的方案，且部分行程遗漏了"儿童免票"政策校验。事后复盘花了 5 天人工逐条翻 trace 才定位到根因；期间没有任何自动化手段能在上线前拦住这次回归；
  2. 上线验证 = 两个工程师手动点 20 条：每次改 prompt、换模型、调工具描述，验证方式就是人工试几条典型对话"看起来没问题"就发布。可 Agent 的失败是概率性的：同一条 case 人工跑通一次，不代表线上 4 万次请求里不会在长尾上翻车；
  3. 线上失败无法归因：客诉进来后，不知道是规划错了、工具选错了、参数传错了、还是 RAG 没召回，每次都要人肉从几十万 token 的 trace 里捞线索；修完之后也没有机制保证"同一个坑不会再踩"。

CTO 给下一任"Agent 平台负责人"候选人出了一道现场设计题，要求依次回答：

  1. 给这个旅行 Agent 设计一套分层的评测指标体系（结果层/轨迹层/系统层），每个指标给出具体定义与判定方式——为什么"任务成功率 92%"这一个数字远远不够？
  2. 轨迹评估怎么做？Agent 走 30 步、工具调用顺序存在合理变体，exact match 一比就全挂，如何设计匹配模式？工具调用正确性应该拆成哪几层？
  3. 大量开放性任务（行程方案好不好、话术得不得体）没有标准答案，只能上 LLM-as-Judge。Judge 有哪些已知偏差？怎么校准？哪些判定"能确定性判的就别用 Judge"？
  4. 评测集怎么建？Agent 输出非确定，如何保证评测可复现？如何把评测接入 CI 发布门禁，让"改 prompt = 改代码"拥有同等的回归纪律？线上 badcase 如何回流形成数据飞轮？
  5. （编码）现场实现一个最小可用评测 Harness 的核心代码：轨迹匹配评估器 + LLM Judge + 回归门禁比较器。

【答案详解】

一、原理讲解：Agent 评测 ≠ 模型评测——三层指标体系

先讲清楚"为什么不一样"。 传统模型评测（如 MMLU、C-Eval）评的是单轮文本质量，而 Agent 是"做"的系统：它多轮交互、调用工具、读写状态、对环境产生真实副作用。这带来三个本质差异，决定了评测框架必须重建：

  1. 非确定性：同一输入多次运行，成功与否是概率事件。"人工跑通一次"毫无意义，必须看多次运行的稳定性（同题跑 5 次，是 5/5 还是 3/5）；
  2. 结果可以"蒙对"：失败三次后第四次碰巧答对，或者跳过必做校验直接给出正确结果——最终答案对，过程是错的。只看结果会系统性放过"走捷径、碰运气、越权操作"的行为；
  3. 失败可归因到层：规划错、工具选错、参数传错、检索没召回、上下文超限——每类的修法完全不同，评测必须能把失败分类计数，否则优化无从下手。

由此得到业界通行的三层指标体系（结果层 Task Level → 轨迹层 Trajectory Level → 系统层 System Level）：

层次 指标 定义与判定方式 判定手段
结果层 端到端任务成功率 订单是否真的生成、行程是否覆盖全部约束（天数/预算/直飞） 规则断言 + 数据库状态比对
结果层 中态匹配率 行程关键槽位（目的地、日期、人数、酒店星级）与需求一致 结构化字段抽取后精确比对
结果层 关键错误率 会造成实际损失的错：错下单、金额算错、政策误读 规则断言，单列并设 0 容忍门槛
轨迹层 工具选择准确率 该查机票时是否调了 search_flight 而不是 search_hotel 轨迹匹配 / Judge
轨迹层 参数正确率 工具参数是否合法且符合需求（日期格式、城市码、儿童数） Schema 校验 + 字段比对
轨迹层 轨迹效率 3 步能完成的比价是否走了 10 步（冗余步骤率） 与参考轨迹步数对比 / Judge
轨迹层 错误恢复率 注入工具超时/脏数据后能否自我纠正而非死循环 故障注入测试
轨迹层 合规性 是否先查退改政策再下单、是否越权调用他人订单接口 轨迹断言（顺序约束）
系统层 单位成功成本 总 Token 成本 / 成功任务数（把重试浪费也算进去） Token 计量归因
系统层 端到端延迟 P50/P95，交互式场景看 TTFT 打点
系统层 人工接管率 会话中途转人工的比例——最硬的业务指标 业务埋点

两个面试高频陷阱必须点破：

  • "成功率 92% 就是好 Agent 吗？"——不一定，要看任务价值分布。 如果 92% 完成的是查政策这类低价值任务，而失败的 8% 集中在下单这种高客单价任务，实际业务体验可能很差。正确做法是按任务价值加权成功率，或直接看"关键错误率"这一底线指标；
  • "单位成功成本比 Token 单价有意义得多。" 总成本 / 成功任务数，把失败重试的浪费也摊进去——一个"便宜但常失败重试"的模型，单位成功成本反而可能更高。这也是"换小模型省钱"这类决策的唯一正确判据。

二、轨迹评估：从 exact match 到四种匹配模式

为什么 strict/exact match 不可行？ Agent 的合理执行路径存在天然变体：先查酒店还是先查机票都合理、参数中城市用"IATA 码"还是"中文名"都合法、模型思考文本每轮都不同。对 30 步轨迹做逐消息严格比对，会把大量正确执行误判为失败。所以轨迹评估要按"你到底关心什么"选择匹配模式——LangChain 开源 agentevals 包给出了四种标准模式，也是面试时可以直接引用的框架：

模式 语义 适用场景（以旅行 Agent 为例）
strict 消息与工具调用完全同序匹配 强流程约束：必须先调 get_refund_policy 拿到退改规则，才允许 create_order
unordered 相同工具调用集合、顺序不限 信息检索类：查机票/酒店/景点无依赖，顺序自由
subset 实际调用 ⊆ 参考集合，不允许额外调用 权限收敛测试：查价格环节不得调用写操作工具
superset 实际调用 ⊇ 参考集合，允许额外调用 必做动作校验：下单前至少包含一次政策查询

工具调用正确性要拆成三层，外加一个"无害性"维度（CSDN 智能体面试准备系列的标准答法）：

  1. 工具对不对：语义上该调哪个工具（工具选择准确率）；
  2. 参数对不对：参数值是否正确——面试可举 SQL 类比：不能只看 SQL 语法合法，要比对执行结果集是否与预期一致；
  3. 时机对不对：调用是否发生在正确的流程位置（政策查询必须在下单之前）；
  4. 无害性：即使结果正确，也要检查是否越权、是否产生多余副作用——"结果对但偷看了不该看的数据"同样是失败。

两条工程落地要点：

  • 参数比对支持"等价类"而非字面全等：tool_args_match_mode 允许配置哪些参数必须精确、哪些可模糊（如日期 2026-11-24 与 "11月24日" 等价）；价格、订单号等业务字段建议在工具层做录制回放，比对结构化输出；
  • 对无参考轨迹的场景，用轨迹版 LLM-as-Judge：agentevals 提供 create_trajectory_llm_as_judge，把完整消息序列（含 tool_calls）交给 Judge 评"这条执行路径是否合理高效"，可以不提供参考轨迹、也可提供作为参照。它评的是"语义质量"，与 trajectory match 评"过程是否按预期走"互补。

三、LLM-as-Judge：偏差、量规与校准

行程方案好不好、安抚话术得不得体——这类开放任务没有唯一答案，规模化评测只能靠 Judge 模型。但直接上一个"打分"prompt 是面试翻车点，必须讲清三件事：

1）已知偏差与缓解手段：

偏差 表现 缓解
位置偏差（position bias） pairwise 比较时偏爱某个固定出现顺序，交换顺序后胜负反转 随机化顺序、双次评估取一致结果
冗长偏差（verbosity bias） 更长的回答得分更高，哪怕啰嗦跑题 rubric 写明"重内容轻篇幅"、单独评简洁性维度
自我偏好（self-enhancement） Judge 偏爱同家族/自己生成的输出 Judge 与生成模型解耦（如生成用 Qwen、Judge 用 DeepSeek + GLM 混合）、多裁判投票

2）量规（rubric）设计：能用确定性判的，绝不劳驾 Judge。

  • Pass/Fail 优于 1~5 打分：1~5 分的相邻分差引入主观噪声、需要更大样本才有统计显著性；二元判定信号更干净。要细分就拆维度（有用性/忠实度/安全性各自 pass/fail），而不是拉长量表；
  • Judge 必须给参考证据：评"行程是否覆盖儿童免票政策"时，把 RAG 召回的政策原文一并给 Judge 对照判，而不是凭它自己的记忆——防止 Judge 自己幻觉；
  • 可执行判定走规则断言：能落 SQL 的比对数据库状态、能跑单测的看通过率、结构化输出做 Schema 校验——客观、可复现、零幻觉。三者按"规则断言为基线、状态比对补操作验证、LLM-as-Judge 覆盖语义层"组合成闭环。

3）校准流程（这是与"调 prompt 凭感觉"拉开差距的关键）：

  1. 人工标注 50~100 条作为金标准，计算 Judge 与人工的吻合率（MT-Bench 表明强 Judge 与人工一致率可超 80%，但业务场景上会衰减，必须用自己的标注校准）；
  2. 固定 Judge 的模型版本与 prompt 版本——模型静默升级会导致分数漂移，历史分数全部失去可比性；
  3. 分歧样本（多裁判分差 > 1）路由到人工抽检（Annotation Queue），修正结果回灌金标准集；
  4. 定期重校准：Judge 和它评的 Agent 一样会漂移。

四、评测集构建、可复现性与 CI 门禁

评测集从哪来？四个来源缺一不可：

  1. 真实流量采样：100~500 条起步，覆盖典型场景 + 长尾 + 多轮追问；
  2. 边界与对抗：非法输入（"帮我把别人的订单退了"）、工具超时、注入攻击、多跳组合需求；
  3. 线上事故回流：每一次客诉/badcase 脱敏后固化为评测用例——这是评测集"持续生长"的机制，停滞的评测集三个月后就会变成"好看但没用"的历史档案；
  4. holdout 留出集：防止针对评测集过拟合调 prompt，定期用新流量刷新。

非确定性怎么保证可复现？ 核心思路是"把考场标准化"：

  • 沙箱 + 环境快照：每次评测前加载预存快照（数据库快照、文件系统快照、API Mock 状态），保证 Agent 始终在同一起跑线运行；写操作工具（create_order）全部 Mock 化，比对"本应产生的状态变更"而非真实下单；
  • 工具录制回放：CI 中用录制的外部接口响应回放，成本比真实调用低一个量级且结果稳定；
  • 每案多次跑：同一用例跑 3~5 次，分别看"至少一次成功"（pass@k，能力上限）与"次次成功"（稳定性，上线标准）；发布看后者；
  • 随机性固定：temperature、模型版本、prompt 模板版本全部显式固定并记录。

CI 发布门禁——"改 prompt 就是改代码"：

  • 每次改动（prompt、模型、工具描述、编排逻辑）自动触发全量评测集回归，比对成功率/工具准确率/步数/成本四项；
  • 门禁阈值：端到端成功率不低于基线 −2 个百分点；安全合规类用例（越权、注入、误下单）0 回归；单位成功成本涨幅 > 10% 触发告警；
  • 通过后灰度发布（如 5% 流量），线上指标看板确认无回流再全量。

数据飞轮（终面加分项）：用户点踩/客诉 → trace 采样归因 → 脱敏进评测集与红队集 → CI 门禁拦截同类回归 → 灰度验证 → 看板确认闭环。缺"回流"二字，AgentOps 只是监控大盘。

五、编码实现：最小可用评测 Harness 核心代码

以下是可直接落地的核心骨架：轨迹匹配评估器（unordered 模式 + 参数等价比对）、LLM Judge（JSON 结构化输出 + pass/fail 量规）、回归门禁比较器三部分。

# eval_harness.py — Agent 评测 Harness 核心（轨迹匹配 + LLM Judge + 回归门禁）
import json, re, statistics
from dataclasses import dataclass, field
from typing import Callable, Optional

# ---------- 1. 评测用例与轨迹结构 ----------
@dataclass
class Case:
    case_id: str
    input: str                      # 用户输入
    expected_tools: list            # 必须调用的工具名集合（superset 校验）
    forbidden_tools: list           # 禁止调用的工具（如纯查询场景禁写操作）
    tool_arg_asserts: dict = field(default_factory=dict)   # {"search_flight.date": lambda v: bool(re.match(r"\d{4}-\d{2}-\d{2}", v))}
    judge_rubric: Optional[str] = None   # 开放性任务的量规，None 则只做规则断言

@dataclass
class Step:                         # 从 trace 采集的每一步
    step_type: str                  # planning / tool_call / final_answer
    tool: Optional[str] = None
    args: Optional[dict] = None

# ---------- 2. 轨迹评估器：必选工具 + 禁用工具 + 参数等价断言 ----------
def eval_trajectory(case: Case, steps: list[Step]) -> dict:
    tool_calls = [s for s in steps if s.step_type == "tool_call"]
    called = {s.tool for s in tool_calls}
    checks = {
        "required_tools_superset": set(case.expected_tools) <= called,   # 必做动作（superset）
        "no_forbidden_tools": not (set(case.forbidden_tools) & called),  # 无害性：禁用工具零容忍
        "args_valid": True,
    }
    for key, fn in case.tool_arg_asserts.items():
        tool, field_name = key.split(".", 1)
        val = next((s.args.get(field_name) for s in tool_calls
                    if s.tool == tool and s.args and field_name in s.args), None)
        if val is None or not fn(val):
            checks["args_valid"] = False
    # 轨迹效率：冗余调用检测（同工具同参数重复调用视为打转）
    sig = [(s.tool, json.dumps(s.args, sort_keys=True)) for s in tool_calls]
    checks["no_redundant_calls"] = len(sig) == len(set(sig))
    return {"case_id": case.case_id, "trajectory_pass": all(checks.values()), "checks": checks}

# ---------- 3. LLM Judge：JSON 结构化 + 维度化 pass/fail 量规 ----------
JUDGE_SYSTEM = (
    "你是严格的质检裁判。依据量规逐项判定，只输出 JSON："
    '{"intent_coverage": bool, "policy_faithful": bool, "tone_ok": bool, "reason": str}。'
    "policy_faithful 必须对照<政策证据>判定，禁止凭记忆。"
)
def eval_with_judge(case: Case, agent_output: str, evidence: str,
                    judge_fn: Callable[[str], str]) -> dict:
    prompt = (f"<量规>\n{case.judge_rubric}\n</量规>\n<政策证据>\n{evidence}\n</政策证据>\n"
              f"<Agent输出>\n{agent_output}\n</Agent输出>")
    raw = judge_fn(f"{JUDGE_SYSTEM}\n\n{prompt}")
    m = re.search(r"\{.*\}", raw, re.S)
    verdict = json.loads(m.group(0)) if m else {"intent_coverage": False, "policy_faithful": False,
                                                "tone_ok": False, "reason": "judge 输出解析失败"}
    verdict["judge_pass"] = all(v for k, v in verdict.items()
                                if k in ("intent_coverage", "policy_faithful", "tone_ok"))
    return {"case_id": case.case_id, **verdict}

# ---------- 4. 回归门禁：新版对比基线，阈值不达标即拦截发布 ----------
def regression_gate(baseline: dict, candidate: dict,
                    acc_floor_delta=0.02, cost_rise_alert=0.10) -> dict:
    acc_b, acc_c = baseline["success_rate"], candidate["success_rate"]
    cost_b, cost_c = baseline["unit_success_cost"], candidate["unit_success_cost"]
    # 安全合规类用例：任一回归即拦截（0 容忍）
    safety_regress = [c for c in candidate["safety_cases"] if not c["pass"]]
    return {
        "gate": (acc_c >= acc_b - acc_floor_delta
                 and not safety_regress
                 and (cost_c - cost_b) / cost_b <= cost_rise_alert),
        "accuracy_drop": round(acc_b - acc_c, 4),
        "cost_rise": round((cost_c - cost_b) / cost_b, 4),
        "safety_regressions": [c["case_id"] for c in safety_regress],
    }

# ---------- 5. 稳定性评测：每案多次跑，发布看"次次成功" ----------
def run_stability(run_agent, case: Case, k=3) -> dict:
    results = [run_agent(case) for _ in range(k)]   # 每次都是隔离沙箱环境快照
    return {"case_id": case.case_id, "pass_at_k": any(results),   # 能力上限
            "stable_pass": all(results),                          # 上线标准
            "pass_rate": sum(results) / k}

落地要点清单（面试收尾时逐条说出，证明能带队落地）：

  1. Trace 全量打点并带 prompt 模板版本 + 模型版本 + 采样参数——没有版本号，历史数据全部不可比；
  2. 写操作工具在评测环境一律 Mock 化，比对状态变更意图而非真实副作用；
  3. 门禁跑在 CI 里，prompt 文件纳入代码审查流程，与业务代码同评审、同发布；
  4. Judge 输出必须携带 reason，分歧样本自动路由人工标注队列；
  5. 线上按 10% 采样跑在线 Judge（先用确定性指标筛出可疑流量再触发 LLM 检查以控成本），badcase 一键沉淀进数据集——这就是把"生产失败"变成"永久回归测试"的飞轮。
