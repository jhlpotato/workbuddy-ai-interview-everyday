2026-11-23 · AI Infra × AI Agent 推理服务优化

【方向】

AI Infra × AI Agent — Agent 工作负载的推理服务优化（Prefill/Decode 两阶段原理、PagedAttention 与 Continuous Batching、前缀缓存 Prefix Caching / RadixAttention、KV Cache 显存治理与分级缓存、Chunked Prefill 与 PD 分离，理论原理 + 系统设计 + 部署落地配置与代码）

【题目及项目背景】

某互联网公司 AI 中台为旗下多条业务线（智能客服 Agent、数据分析 Agent、运营文案 Agent）提供统一自建推理服务：后端是一个 vLLM 集群（8 卡 A100-80G，按业务划分实例池），模型为 Qwen 系列 14B/32B；上层是模型网关，负责路由、限流与计费。Agent 侧特点非常鲜明：每个 Agent 的请求都带一段约 4000~6000 token 的固定前缀（System Prompt + 全量工具 Schema + 少量 Few-shot 示例），多轮会话逐轮追加历史，一次复杂任务往往产生 20~40 次模型调用（每次工具调用都是一轮新请求）。

灰度上线两个月后，推理服务暴露四类典型问题：

  1. 首 Token 延迟（TTFT）高达 3~5 秒：同一段 System Prompt 与工具 Schema 每次请求都被完整重算一遍 Prefill，用户在对话框前干等，体验远差于直接调用商用 API；
  2. 并发上不去且偶发 OOM：长上下文会话的 KV Cache 占用随轮次线性膨胀，传统框架按最大长度预分配导致 60%~80% 显存被浪费，业务高峰期频繁触发抢占与重算，P99 延迟雪崩；
  3. 在线与离线互相踩踏：数据分析 Agent 的批量子任务（Fan-out 并行拉数据）把 GPU 打满，在线客服对话被挤出调度队列，夜间批量任务又让 GPU 空转，资源错配严重；
  4. 成本归因不清：网关只统计了 prompt_tokens，没有人说得清"每次请求到底有多少 token 是重复计算"，优化无从下手。

面试题：请给出该推理服务的完整优化设计方案，重点阐述：① Prefill 与 Decode 两阶段的本质差异（Compute-bound vs Memory-bound）与推理服务的核心指标体系（TTFT/TPOT/吞吐/P99）；② PagedAttention 与 Continuous Batching 的原理，为什么二者能让同卡并发提升 2~4 倍；③ 面向 Agent 场景的前缀缓存（vLLM APC / SGLang RadixAttention）原理，以及提示词结构如何设计才能把命中率从 20% 提到 80% 以上；④ 进阶优化组合拳：Chunked Prefill、PD 分离、KV Cache 量化与分级缓存、投机解码、在线/离线优先级调度分别解决什么问题、适用边界是什么；⑤ 手写可落地的 vLLM 部署配置与 Agent 侧"前缀编排器"代码（稳定前缀组装、块对齐、命中率统计）。

【答案详解】

一、原理讲解：Prefill 与 Decode 的本质差异——推理优化的第一性原理

LLM 推理分两个阶段，瓶颈性质完全不同，所有优化手段都能归到这两个阶段上：

维度 Prefill（预填充） Decode（解码）
做什么 一次性处理完整 prompt，逐层算出全部 token 的 KV Cache 自回归每次只算 1 个新 token
计算形态 稠密 GEMM（大矩阵乘），算力密集 矩阵向量乘 GEMV，访存密集
瓶颈 Compute-bound（算力瓶颈） Memory-bound（访存带宽瓶颈），瓶颈在读权重与 KV Cache 的显存带宽
决定指标 TTFT（首 Token 延迟） TPOT/ITL（每 Token 生成间隔）

由此得出推论：

  • TTFT ≈ prompt 长度 × Prefill 计算效率。Agent 场景每次请求都携带几千 token 的固定前缀，TTFT 自然居高不下——这是题目中问题 1 的根因。优化的两条路：让前缀少算（前缀缓存）、让长 prompt 不阻塞别人（Chunked Prefill / PD 分离）；
  • Decode 慢的本质是"每生成 1 个 token 都要把全部权重读一遍显存"。Continuous Batching 的真正价值，就是让多个请求复用同一次权重读取，把 Decode 的 GEMV 重新"攒回"GEMM，摊薄访存开销；
  • KV Cache 是自回归推理的结构性成本：它随上下文长度 T 与并发数 B 线性膨胀（近似 B × T × 层数 × KV头数 × 头维度 × 2字节）。线上服务"GPU 利用率不高但吞吐上不去"，多数时候不是算力到顶，而是显存装不下足够多的并发序列——这是问题 2 的根因。

指标体系必须先立起来：TTFT（P50/P99）、TPOT/ITL、端到端时延、吞吐（tokens/s 与 requests/s）、显存水位与 KV Cache 块利用率、（自建场景独有）前缀缓存命中率与 cached_tokens。没有这组仪表盘，后面所有优化都只是"压测大冒险"。

二、两大基石：PagedAttention 与 Continuous Batching 为什么能让并发提升 2~4 倍

传统 KV Cache 管理的三宗罪（这也是面试官最爱追问的"为什么要发明 PagedAttention"）：

  1. 按最大长度预分配（内部碎片）：请求到来时按 max_model_len 一次性预留一整块连续显存。绝大多数请求只生成几百 token，预留空间的 60%~80% 被白白闲置，且不能给别人用；
  2. 必须物理连续（外部碎片）：请求不断创建销毁后，显存被切成蜂窝煤——空闲总量够，但凑不出一段连续大块，新请求只能干等，甚至"显存看着还有却 OOM"；
  3. 无法跨请求复用：100 个请求共享同一段 System Prompt，前缀 KV 却各存 100 份、各算 100 遍。

PagedAttention 的解法：把操作系统的虚拟内存分页搬进 GPU——

  • 把 KV Cache 切成固定大小的物理块（block，默认 16 token/块），放入全局块池；
  • 每个序列维护一张 block table（块表），把"逻辑上连续的 token 位置"映射到"物理上不连续的显存块"；
  • 按需分配：序列增长越过块边界时才领新块，浪费上界从"绑定最大长度"降为"最多浪费最后一个没填满的块"；
  • 前缀共享 + Copy-on-Write：多个请求/分支的块表可以指向同一批物理块（引用计数），只在真正需要写入共享块时才复制——这是前缀缓存和 beam search 省显存的机制基础；
  • 代价是注意力 kernel 必须支持从非连续块中读取 KV（vLLM 重写了 CUDA kernel），这也是它"不只是内存分配器"的原因。

Continuous Batching（连续批处理）：静态 batch 必须"同时开始、同时结束"，短请求在长请求的尾部完全空转。Continuous Batching 把调度粒度下沉到每个 decode 迭代步：某请求生成完立即退出、归还块池，新请求下一个迭代步直接插入 batch。GPU 槽位始终满载。

二者是绑定关系：Continuous Batching 让"驻留序列集合"每一步都在变化，连续大块分配会碎成一地；而块池按块领用天然适配这种动态进出。论文与生产实测的结论一致：同卡可驻留请求数提升 2~4 倍，吞吐同步提升。

三、Agent 场景的王牌：前缀缓存（APC / RadixAttention）与提示结构工程

这是本题的题眼：Agent 工作负载中 60%~80% 的 token 是重复前缀（System Prompt + 工具 Schema + 逐轮追加的历史对话）。通用推理框架把每个请求当独立任务，这段前缀被反复重算——"不是推理不够快，是它根本没为 Agent 设计"。

两种实现：

  • vLLM Automatic Prefix Caching（APC）：把 token 序列按 16 token 切块，每块用链式哈希唯一标识，维护全局哈希表；新请求逐块查表，命中的块直接引用物理 KV，只对未命中后缀做 Prefill；
  • SGLang RadixAttention：把所有请求的 token 前缀组织成一棵基数树，树上每个节点持有该段前缀的 KV，天然支持任意深度的前缀共享与逐轮追加复用；对多轮对话、Agent 工具调用这类"前缀高度重复"的场景收益最大（TTFT 可降 50% 以上）。生产实测中，多轮对话/Agent 场景命中率普遍可达 80%~95%，后轮 Prefill 时间趋近于零。

决定收益的不是引擎，而是你的提示结构。命中率从 20% 拉到 80% 以上靠四条工程纪律：

  1. 静态内容全部前置：System Prompt、工具定义、Few-shot 示例放在请求最前面，且逐字节完全一致——差一个空格、一个版本号、一个时间戳，缓存链从该处全断；
  2. 动态内容全部后置：把"当前时间"、检索结果、用户消息放在末尾；知识库版本号这类准静态字段移到请求末尾；
  3. 历史逐轮完整拼接，不拆不重排：多轮对话必须保持完整前缀链（第 N 轮的 prompt 必须是第 N-1 轮 prompt + 追加内容），不能做历史裁剪/摘要后重排——一旦前缀中间变化，后面全部失效；
  4. 前缀按块对齐：缓存以 16 token 的物理块为单位，前缀长度不是块大小整数倍时最后一块无法复用（这是源码里的真实边界，部署极易踩坑）；工具描述顺序固定，不要让 JSON 序列化顺序抖动。

引擎选型（一句话版）：TTFT 敏感的对话式 Agent → SGLang（RadixAttention 精确前缀匹配）；吞吐优先的 SaaS 通用服务、模型覆盖面广 → vLLM（Continuous Batching 更成熟、生态更大）。两者都有 OpenAI 兼容接口，迁移成本主要在调参与回归验证。

四、进阶优化组合拳：每个手段解决什么问题、边界在哪

手段 解决什么 适用边界 / 注意点
Chunked Prefill 把长 prompt 切块处理，允许 Decode 请求插队计算，削平长请求造成的延迟毛刺 P99 TTFT 显著改善；略微牺牲单请求 Prefill 效率
PD 分离（Prefill/Decode 分离部署） Prefill 吃算力、Decode 吃带宽，拆到不同实例各自做满硬件；长 prefill 不再阻塞 decode 架构与调度复杂度上升，KV 需要跨实例传输；流量大且负载混合时才值得
KV Cache 量化（FP8/INT8） KV 显存直接减半 → 更长上下文或更高并发 KV 对精度不敏感，损失通常可忽略；与权重量化独立配置，上线前跑评测集回归
权重量化（AWQ/GPTQ/INT4） 70B 从 140GB 降到 35GB 级别，2 张卡即可部署 代码/数学任务精度敏感，从 INT8 起步逐级验证；AWQ 在 vLLM 上算子融合度较好
分级 KV 缓存（HiCache/FlexKV 类） 把冷 KV 逐层下沉到主机内存/SSD/分布式存储，"以存换算" 长会话、高前缀重复场景收益大；业界实测可将首字时延降低 50%~70%
投机解码（Speculative Decoding） 小模型先草稿多个 token、大模型一次并行验证，降低 Decode 延迟 适合低并发、延迟敏感场景；高并发时 batch 已填满 GPU，收益有限
优先级调度 / 资源隔离 在线对话与离线批量任务分队列、分实例池，保障在线 SLA 配合网关侧按业务路由；生产调优重点常不在模型侧而在调度侧
模型路由 简单请求走小模型/缓存，复杂请求走大模型 网关按意图分类 + 成本预算路由，是最便宜的大盘优化

落地顺序建议（性价比从高到低）：立指标基线 → 开前缀缓存并做提示结构工程 → KV/权重量化 → Chunked Prefill → 调度隔离 → 视流量规模上 PD 分离与分级缓存。社区实测，"量化 + 连续批处理 + 前缀缓存"三步走完，单卡吞吐普遍提升 2~4 倍，Agent 场景 TTFT 可从秒级压到百毫秒级。

五、编码实现：可落地的 vLLM 部署配置 + Agent 前缀编排器

5.1 生产级启动配置（每个参数为什么这么给，都要能讲出来）

# 生产级 vLLM 启动配置（Qwen 32B, A100-80G, Agent 场景）
python -m vllm.entrypoints.openai.api_server \
  --model /models/Qwen2.5-32B-Instruct-AWQ \
  --served-model-name qwen-32b \
  --gpu-memory-utilization 0.92 \        # 显存预算：权重 + KV 块池 + 激活；调高 = KV 池更大、前缀缓存存得更多
  --max-model-len 32768 \                # 按业务 P99 设，不要开到模型上限——长序列会把 KV 块池占满、缓存条目变少
  --max-num-seqs 64 \                    # 单批最大序列数；与 max-model-len 联动，调过大反而碎片化
  --block-size 16 \                      # 块大小：前缀必须按 16 token 对齐才能整块命中
  --enable-prefix-caching \              # 核心：自动前缀缓存（V1 引擎默认开启，显式写出来防回退）
  --enable-chunked-prefill \             # 长 prompt 切块，Decode 可插队，削 TTFT 毛刺
  --kv-cache-dtype fp8 \                 # KV Cache FP8 量化：显存减半，精度损失可忽略（需评测回归）
  --enable-prompt-tokens-details \       # usage 返回 cached_tokens，用于统计命中率与成本归因
  --disable-log-requests

5.2 Agent 侧前缀编排器：缓存的命中率是"编排出来的"，不是引擎自己长出来的。

# prefix_orchestrator.py — Agent 请求的前缀编排与命中率监控
import json, time
from collections import OrderedDict
from openai import OpenAI

client = OpenAI(base_url="http://vllm-gw.internal:8000/v1", api_key="EMPTY")
BLOCK_SIZE = 16  # 与 vLLM --block-size 一致，用于前缀块对齐检查

class PrefixOrchestrator:
    """
    核心原则：
    1. 稳定前缀（system prompt + 工具 schema）逐字节冻结，按工具注册顺序固定序列化；
    2. 会话历史逐轮"完整拼接"（第 N 轮 prompt = 第 N-1 轮 prompt + 追加），永不重排/裁剪前缀；
    3. 动态内容（时间戳、检索结果、用户消息）一律后置；
    4. 每个 Agent 的稳定前缀做指纹缓存与命中率统计。
    """

    def __init__(self):
        self._frozen_prefix: "OrderedDict[str, str]" = OrderedDict()  # agent_id -> 冻结前缀
        self._stats = {}  # agent_id -> {"prompt": int, "cached": int}

    # ---- 1) 稳定前缀：只允许在部署时构建一次，运行期不可变 ----
    def freeze_prefix(self, agent_id: str, system_prompt: str, tools: list[dict]) -> str:
        # 关键：工具列表按注册序固定排序，json.dumps 键序确定（sort_keys），
        # 否则每次序列化顺序抖动会把缓存链打断在第一个不一致的字节处
        tool_block = "\n".join(
            json.dumps(t, ensure_ascii=False, sort_keys=True) for t in tools
        )
        prefix = f"<system>\n{system_prompt}\n</system>\n<tools>\n{tool_block}\n</tools>\n"
        self._frozen_prefix[agent_id] = prefix
        return prefix

    # ---- 2) 组装完整 prompt：冻结前缀 + 完整历史链 + 动态后缀 ----
    def build_prompt(self, agent_id: str, history: list[str], user_msg: str,
                     retrieved: str | None = None) -> str:
        prefix = self._frozen_prefix[agent_id]
        # 历史按原顺序完整拼接；若业务必须截断历史，请整段截断并更换会话指纹
        # （截断后的前缀与旧会话不同，会自然建立新的缓存分支，而不是污染旧链）
        hist = "".join(history)
        tail = ""
        if retrieved:                       # 动态内容只出现在尾部
            tail += f"<context>\n{retrieved}\n</context>\n"
        tail += f"<user>\n{user_msg}\n</user>"
        return prefix + hist + tail

    # ---- 3) 调用并统计命中率：cached_tokens 是自建推理的成本归因命脉 ----
    def chat(self, agent_id: str, prompt: str, max_tokens: int = 1024) -> str:
        resp = client.completions.create(
            model="qwen-32b", prompt=prompt, max_tokens=max_tokens, temperature=0.3,
        )
        usage = resp.usage
        st = self._stats.setdefault(agent_id, {"prompt": 0, "cached": 0})
        st["prompt"] += usage.prompt_tokens
        st["cached"] += getattr(usage, "cached_tokens", 0) or 0
        return resp.choices[0].text

    def hit_rate(self, agent_id: str) -> float:
        st = self._stats[agent_id]
        return st["cached"] / st["prompt"] if st["prompt"] else 0.0

    # ---- 4) 块对齐自检：前缀长度不是 block_size 整数倍时，最后一块永不命中 ----
    def assert_block_aligned(self, agent_id: str) -> bool:
        n = len(self._frozen_prefix[agent_id].split())  # 近似 token 数
        ok = n % BLOCK_SIZE == 0
        if not ok:
            # 生产上用 pad token 或微调模板长度补齐到块边界
            print(f"[WARN] {agent_id} prefix tokens={n} 未对齐 {BLOCK_SIZE}，最后一块无法复用")
        return ok


if __name__ == "__main__":
    orch = PrefixOrchestrator()
    orch.freeze_prefix("cs_agent", "你是客服 Agent…（约 4000 token 冻结）", TOOLS)
    orch.assert_block_aligned("cs_agent")

    h = []
    for turn in range(5):  # 模拟 5 轮多轮对话
        prompt = orch.build_prompt("cs_agent", h, f"用户第 {turn+1} 条消息")
        orch.chat("cs_agent", prompt)
        h.append(f"<assistant>…第 {turn+1} 轮回复…</assistant>\n")
        print(f"turn {turn+1}: 命中率 = {orch.hit_rate('cs_agent'):.1%}")
    # 预期输出：turn1 命中率低（首次计算），turn2 起稳定前缀 + 历史链整段命中，收敛到 80%+

5.3 监控与验收：用 vLLM 自带 benchmark_serving.py 以真实"脏负载"压测（60% 请求共享固定长前缀 + 40% 随机长度），验收口径写进 SLA——TTFT P99、吞吐 tokens/s、前缀命中率（cached_tokens/prompt_tokens）、显存水位与抢占次数。网关侧再按业务拆分仪表盘：线上"命中率跌破 60% 告警"通常意味着某个 Agent 改了 System Prompt 或工具顺序而没人知道——前缀缓存把提示词工程从"效果问题"变成了"基础设施契约"。
